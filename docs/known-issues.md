# 已知限制

之後整理進 README 的「已知限制」。

## 非財務表格攤平後的數字仍留在內文 chunk

- **現象**：問「廣達每股盈餘」時，前 5 名裡有 2 個是廣達 p71、p72 的內文 chunk，內容是「股本形成經過」表攤平後黏在一起的數字，例如 `38,000,0003,363,00833,630,080`。正確的表格 chunk（p104 經營結果比較分析）排第 3 名。
- **原因**：ingestion 只會跳過「已抽成表格 chunk」的 bbox 範圍內的內文。股本表所在頁沒有財務概況關鍵字，項目欄也沒有財務項目，所以沒被抽成表格，攤平文字就留在內文裡。查詢裡的「每股盈餘」和表中的「每股面額」字面相近，因此排名偏高。
- **目前的處理**：接受現況。`/ask` 取前 8 名，表格 chunk 排在 context 最前面，prompt 要求數字以表格為準。
- **可能的修法**：全書用 pdfplumber 偵測格線表格的範圍，只用來排除內文（ingestion 會變慢，非財務表的內容也會從資料庫消失）；或偵測數字密集、數字黏連的 chunk 後丟棄或降權。

## 回答裡的引用編號 [n] 可能指錯段落

- **現象**：問「廣達 2025 年每股盈餘是多少？」，數字 19.45 元答對了，但有一次回答標成 [2]（p103 資產負債表）。數字其實出自 [1]（p104 經營結果比較分析）和 [3]（p5 致股東報告書）。temperature 0.1 下，同一題每次標的編號不一定相同。
- **原因**：[n] 是 qwen3.5:2b 自己寫的，小模型不一定照 prompt 規則把數字對應回正確段落。
- **影響範圍**：`sources` 事件由程式組成，編號與 context 的 [1]…[8] 一致，所以來源清單本身是正確的；只有回答文字裡的 [n] 可能指到錯的段落。
- **可能的修法**：評估階段（`eval/`）加一項引用正確率，檢查被引用的段落是否真的含有回答裡的數字；或由程式比對回答裡的數字出現在哪些段落，再自動標上或修正編號。

## LLM 回答可能無限生成，沒有總時間或長度上限

- **現象**：held-out 驗收時，h01「聯發科現在的執行長是誰？」的回答持續生成超過 21 分鐘沒有結束，只能手動中止（2026-10-22）。同樣的問題也會發生在 `/ask`：前端會一直顯示「回答中」。
- **原因**：`OllamaChat` 的 httpx timeout（120 秒）是「單次讀取」的逾時，只要模型持續輸出 token 就不會觸發；呼叫 Ollama 時也沒有設定 `num_predict`（最大輸出 token 數）。小模型偶爾會陷入重複輸出。
- **影響範圍**：單題卡住會讓評估整批停住（題目依序執行），線上則會占住模型、讓後續請求排隊。
- **可能的修法**：Ollama options 加上 `num_predict`（例如 512）；後端對整個回答設總時間上限（例如 `asyncio.timeout(60)`），逾時送 `error` 事件；評估程式記錄逾時題目並繼續下一題。

## 小模型把「去年」讀成前一年度（未解決，記錄未來方向）

- **現象**：比較表與內文常並列兩個年度，qwen3.5:2b 偶爾把「去年」當成民國 113 年、讀錯欄位（例如鴻海 EPS 答成 11.01 元；held-out h03 台達電毛利率用 113 年度數字算成 32.41%）。
- **試過、已撤回的做法**：在 prompt 寫明年報年度並定義「去年」（改進 2a）。主評估集上修好 2 題、卻讓另外 4 題明確寫出「去年（即民國 113 年）」，整體正確率從 81% 掉到 69%，因此撤回。
- **未來方向（未實作）**：送進 LLM 前由程式把問題裡的「去年」「今年度」替換成明確年度，例如「2025 年（民國 114 年）」，不靠模型理解相對時間。這是看了主評估集結果才想到的，實作後要用新題目驗證。

## 判分規則只檢查「包含」正確答案

- **現象**：held-out h03 的最終答案是錯的（32.41%），但回答裡引述了正確的 34.3%，自動判分算對。
- **影響**：回答正確率可能略為高估；主評估集目前沒有發現同樣情形，但沒有逐題人工複核。
- **可能的修法**：數字題改成擷取回答的「最終數字」再比對，或人工複核所有判為正確的題目。依規定驗收後不修改規則，留待下一輪評估。
